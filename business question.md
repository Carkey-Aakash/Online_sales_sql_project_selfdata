# 21. Database Change Auditing

**Business Question:**
How can database changes be tracked for auditing purposes?

**Implementation:**
A centralized `ChangeLog` table was created to record database changes.

The audit log records:

* Log ID
* Table name
* Operation performed
* Record ID
* Change date
* User who performed the operation

The audit system captures `INSERT`, `UPDATE`, and `DELETE` operations.

**Purpose:**
To maintain a history of database modifications and improve accountability.

---

# 22. Audit Triggers Across Multiple Tables

**Business Question:**
How can changes made to different tables automatically be recorded in the audit log?

**Implementation:**
Database triggers and trigger functions were implemented for the main business tables.

Audit functionality was applied to:

* Products
* Customers
* Orders
* Categories
* Order Items

The triggers automatically insert records into `ChangeLog` whenever supported `INSERT`, `UPDATE`, or `DELETE` operations occur.

**Purpose:**
To automate database auditing without requiring application-level logging for every operation.

# 23. Database Indexing & Query Performance

**Business Question:**
How can database indexes improve query performance?

**Implementation:**

The project includes:

* Inspecting existing indexes
* Clustering the `customers` table
* Creating an index on customer country
* Testing query performance using `EXPLAIN ANALYZE`
* Inspecting category indexes
* Testing category-name searches
* Creating an index on `products.category_id`
* Clustering the products table
* Re-running performance analysis

The indexing work focuses on improving query performance for commonly searched and joined columns.

**Purpose:**
To understand how indexing and physical table organization can affect PostgreSQL query performance.

# 24. Database Views

**Business Question:**
How can database views simplify frequently used queries?

Three views were created to provide reusable representations of business data.

### 24.1 Product Details View

`vw_product_details`

Provides:

* Product ID
* Product name
* Price
* Stock quantity
* Category name

### 24.2 Customer Orders View

`vw_customer_orders`

Provides:

* Customer information
* Number of orders
* Total quantity/value information from orders

### 24.3 Recent Orders View

`vw_recent_orders`

Provides orders created within the defined recent-period condition.

The three views are implemented in the SQL project as reusable database objects.

**Purpose:**
To simplify complex queries, improve reusability, and provide convenient access to commonly required business information.

# 25. Role-Based Access Control (RBAC)

**Business Question:**
How can database access be controlled based on different user responsibilities?

**Implementation:**
PostgreSQL roles and privileges were implemented to demonstrate database security and controlled access.

The project includes a login user, permission roles, `GRANT`, `REVOKE`, schema permissions, table permissions, and privilege verification.

---

## 25.1 Sales User and Permission Role

A login user named `sales_user` was created.

A separate permission role named `sale_role` was also created and assigned specific database privileges.

The role demonstrates controlled access to database objects rather than giving every user unrestricted permissions.

---

## 25.2 Permission Verification

Database privileges were checked using PostgreSQL's `has_table_privilege()` function.

The project verifies permissions for:

* Customer `SELECT`
* Order `INSERT`
* Order `UPDATE`
* Product `SELECT`
* ChangeLog `INSERT`

This demonstrates how database permissions can be tested programmatically.

---

## 25.3 Read-Only Role

A `readonly_role` was created with `SELECT` access to the database tables.

**Purpose:**
To allow users to view information without modifying business data.

---

## 25.4 Data Entry Role

A `data_entry_role` was created with `INSERT` permissions for selected tables.

**Purpose:**
To allow authorized users to add new category and order-item records.

---

## 25.5 Product Manager Role

A `product_manager_role` was created with CRUD permissions for product and category data.

CRUD operations include:

* `SELECT`
* `INSERT`
* `UPDATE`
* `DELETE`

**Purpose:**
To support users responsible for maintaining product and category information.

---

## 25.6 Order Processor Role

An `order_processor_role` was created with permissions to:

* View orders
* Update orders

**Purpose:**
To support users responsible for processing and updating order information.

---

## 25.7 Customer Support Role

A `customer_support_role` was created with `SELECT` access to:

* Customers
* Orders

**Purpose:**
To allow support staff to view customer and order information.

---

## 25.8 Marketing Analyst Role

A `marketing_analyst_role` was created with `SELECT` permissions on the required business tables.

**Purpose:**
To allow analysts to access data required for customer and sales analysis without modifying the underlying data.

---

## 25.9 Sales Analyst Role

A `sales_analyst_role` was created with `SELECT` access to:

* Orders
* Order items

**Purpose:**
To provide sales-related analytical access while restricting modification privileges.

---

## 25.10 Inventory Manager Role

An `inventory_manager_role` was created with CRUD permissions for products.

**Purpose:**
To allow inventory users to manage product information and stock-related data.

---

## 25.11 Finance Manager Role

A `finance_manager_role` was created with permissions to:

* View orders
* Update orders

**Purpose:**
To provide controlled access for users working with order-related financial information.

---

## 25.12 Backup Operator Role

A `backup_operator_role` was created with database connection access.

**Purpose:**
To demonstrate a restricted operational role with limited database permissions.

---

## 25.13 Restricted Read Role

A `restricted_read_role` was created to demonstrate column-level access.

Instead of granting access to all customer columns, access was limited to selected customer information such as:

* First name
* Last name
* Email

**Purpose:**
To demonstrate how database permissions can be restricted to specific columns.

---

## 25.14 Temporary Access Role

A `temporary_access_role` was created and initially granted access to the database tables.

The permissions were then revoked.

**Purpose:**
To demonstrate how access can be granted temporarily and subsequently removed using `REVOKE`.

---

## 25.15 Application Role

An `application_role` was created as a login-enabled role with database connection and schema access.

The role was also assigned the `product_manager_role`.

**Purpose:**
To demonstrate how an application account can inherit permissions through an existing role instead of individually assigning every privilege.
